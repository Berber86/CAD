# Сбор и сохранение legal descriptions — как автоматизировать

Коля сказал: фото с Google не нужны, а нужна автоматизация **скачивания и правильного
сохранения описаний нашего и соседних лотов**. Алгоритм он обещал дать завтра; здесь —
наша версия заранее, чтобы завтра было с чем сравнивать, а не начинать с чистого листа.

## 1. Что, по нашим представлениям, он делает руками

1. По адресу/BBL находит участок: borough 5 (Richmond), block, lot.
2. Идёт в **ACRIS** (a836-acris.nyc.gov) → поиск по block/lot → список записей.
3. Выбирает **DEED** (и иногда старый DEED, если новый ссылается на прежнее описание).
4. Открывает образ документа — это **скан без текстового слоя**, 5–15 страниц подряд:
   титульный лист, RP-5217, потом **EXHIBIT A** с метесами и границами.
5. Находит страницу(ы) с «BEGINNING AT A POINT…», скачивает, склеивает в один PDF,
   обрезая лишнее (обложки, передаточную декларацию).
6. Повторяет то же для соседей по меже (в Staten Island это обычно 2–4 лота).
7. Сохраняет в папку проекта под именами вида `LOT 30.pdf`, `LOT 32.pdf` — ровно теми,
   которые понимает Шаг 1.

Если это так, то автоматизировать надо **не «поиск в интернете», а конвейер
«BBL → дело → страницы → проверенный файл с правильным именем»**, где самое ценное —
шаги 5 и 7: обрезка страниц и проверка, что скачанное описание действительно про этот
участок.

## 2. Данные: что можно взять без парсинга сайта

У ACRIS есть открытые выгрузки на NYC Open Data (Socrata, JSON, без ключа), и по ним
список документов по BBL собирается без захода на сайт:

| Набор | ID | Что даёт |
|---|---|---|
| ACRIS Real Property Legals | `8h5j-fqxa` | `document_id` по borough + block + lot (+ `partial_lot`, `easement`, адрес) |
| ACRIS Real Property Master | `bnx9-e6tj` | тип документа (`DEED`, `MTGE`…), `crfn`, даты, сумма |
| ACRIS Real Property Parties | `636b-3b5g` | продавец/покупатель — для человекочитаемой подписи |
| ACRIS Real Property References | `pwkr-dpni` | ссылки документа на другие документы (цепочка «being the same premises…») |
| ACRIS Document Control Codes | `7isb-wh4c` | расшифровка кодов типов документов |

Это важно: **поиск и отбор — по открытым данным**, а на сайт ACRIS мы идём только за
картинками конкретного `document_id` (`…/DS/DocumentSearch/DocumentImageView?doc_id=…`).
Меньше запросов, меньше риска, что сайт «поедет».

**References — недооценённая вещь.** Новый deed часто пишет «being the same premises
conveyed by deed recorded … CRFN …» без метесов. Тогда описание лежит в предыдущем
документе: цепочку можно пройти автоматически, а не гадать, почему в новом deed нет
«BEGINNING AT A POINT».

## 3. Что значит «правильно сохранить» — чек-лист

Файл в папке проекта считается правильным, если выполнено всё:

1. **Полнота.** Все страницы, где есть описание (начало и конец: «…to the point or place
   of BEGINNING»), без обложки и без RP-5217. Страницы записаны в имени файла, чтобы
   Шаг 1 не гадал: `LOT 30_p7-8.pdf`.
2. **Принадлежность.** Это deed именно этого лота: BBL и адрес из Legals, тип из Master,
   а не «похожий» документ соседа. Предварительно — фильтр по BBL; окончательно — см. §5.
3. **Актуальность.** Для текущей границы берётся самый свежий deed с описанием; старые
   deeds сохраняются отдельно как история (по ним видно, менялись ли длины).
4. **Имя.** Имя читает Шаг 1: `LOT <номер>` + `_p<страницы>` (`_p7` или `_p7-8`).
   Всё остальное — в файле-паспорте, чтобы не удлинять имя и не ломать разбор.
5. **Паспорт.** Рядом `LOT 30.json`: BBL, `document_id`, CRFN, тип, дата записи, дата
   документа, стороны, страницы, URL, дата скачивания, лицензия/источник. Через год
   без этого невозможно понять, откуда файл.
6. **Текст.** Рядом `LOT 30.txt` — распознанное описание в нормализованном виде (те же
   строки, что понимает наш парсер). Тогда повторный разбор не требует ни PDF, ни ИИ.
7. **Без дублей.** Один `document_id` = один файл. Повторный запуск ничего не качает.

Предлагаемая раскладка:

```
<папка проекта>/
  01_описания/
    LOT 32_p4-6.pdf        # наш участок
    LOT 32_p4-6.txt / .json
    LOT 30_p2-3.pdf        # сосед слева
    LOT 28_p9-10.pdf       # сосед справа
    LOT 34 — нет описания.txt   # чего не хватило
    _manifest.json         # состав набора: файлы, роли, страницы, BBL, итоги проверки
```

`_manifest.json` — то, чего сейчас не хватает больше всего: по нему Шаг 1 может
**поднять весь набор одной кнопкой** («Открыть набор описаний»), уже с ролями (наш /
сосед) и страницами. Сейчас файлы каждый раз выбираются вручную.

## 4. Откуда берутся соседи

Не «все лоты квартала», а только те, что делят межу:

- по нашему адресу: `geosearch.planninglabs.nyc` (бесплатно) → BBL;
- геометрия участка и соседей — MapPLUTO / Digital Tax Map: общие отрезки границы →
  список соседних BBL;
- если участок уже построен по описанию — соседи определяются по общим точкам межи
  (это у нас уже есть в акте сверки);
- роли в наборе: «справа», «слева», «сзади», «через улицу» — по азимуту от центра
  участка на центр соседа (румбы у нас истинные, так что это честные стороны света).

## 5. Проверка, что скачанное описание — про этот участок

Это то, что отличает автоматизацию от «накачал файлов и молись». После распознавания
описание прогоняется тем же движком, что и обычный разбор:

1. парсим метесы и границы → строим полигон;
2. считаем **невязку**: у настоящего deed она мала (доли фута) — если 3 ft, распознавание
   или документ не тот;
3. сравниваем **площадь** с площадью лота по PLUTO/налоговой карте (±5 % — дальше
   объяснять);
4. сравниваем **общие межи**: длины и румбы сторон нашего и соседского полигонов должны
   совпадать (это ровно та сверка, что уже есть в акте сверки);
5. сверяем **название улицы** из описания с адресом лота.

Итог по каждому файлу в отчёте: «LOT 30: deed 1998 г., описание 4 стороны, невязка
0.02 ft, площадь 3 998 sq ft против 4 000 по карте, общая межа 176.92 совпадает —
**принят**»; или «LOT 34: deed 2019 г. без метесов, ссылка на CRFN 2004…, в нём невязка
11.4 ft — **не принят, нужен глаз геодезиста**».

Распознавание берём не «вслепую по всему скану»: сначала дешёвый отбор страниц
(в ACRIS нет текстового слоя, поэтому — рендер страниц в миниатюры и один запрос Vision
«есть ли здесь BEGINNING AT A POINT»), и только найденные страницы идут в полный разбор.
Это экономит и деньги, и время: 15-страничный пакет не уходит в ИИ целиком.

## 6. Модули и порядок работ

| Модуль | Что делает | Зависимости |
|---|---|---|
| `acris.py` | BBL → документы (Legals + Master + References), отбор DEED, скачивание страниц `document_id` с троттлингом и кэшем | `urllib`/`requests`, PyMuPDF для склейки |
| `lots_near.py` | адрес → BBL; соседи по меже; роли «справа/слева/сзади» | geosearch, MapPLUTO |
| `deed_pages.py` | поиск страниц с описанием (миниатюры → Vision), обрезка, склейка | PyMuPDF, существующий `llm_parser` |
| `deed_verify.py` | невязка/площадь/общие межи/улица → «принят / проверить» | существующий движок разбора |
| `deed_store.py` | имена `LOT <n>_p<a>-<b>.pdf`, `.txt`, `.json`, `_manifest.json`, дедуп | — |
| окно Шага 1 | кнопка «📥 Собрать описания по адресу» + «Открыть набор описаний» | `main.py` |

Порядок: `deed_store` (одно и то же нужно и сейчас, руками) → `acris` → `deed_pages` →
`deed_verify` → соседи и роли. Первый полезный результат появляется уже на `deed_store`:
файлы называются правильно и набор поднимается одной кнопкой.

## 7. Аккуратность и право

- ACRIS — публичный реестр, скачивание для своей работы нормально. Но: **не строить
  из этого свою базу для перепродажи**, не публиковать образы документов, в паспорте
  указывать источник.
- Вежливость: не больше 1 запроса в секунду, пауза между документами, кэш скачанного,
  никакого параллельного долбления; при 429/503 — пауза и повтор.
- Скан может быть плохим (микрофильм 1970-х): тогда честное «не распознано, смотреть
  глазами», а не выдуманное описание.

## 8. Что спросить у Коли, когда он покажет свой алгоритм

1. Работает он в ACRIS или в платном сервисе (title company, PropertyShark, TLO)?
   От этого зависит, есть ли вообще автоматизация скачивания.
2. Берёт он **самый свежий** deed или тот, где есть метесы (иногда свежий — на «same
   premises»)? Как решает, что хватит?
3. Как называет файлы и папки? Совпадает ли с `LOT 30.pdf` + `_p<страницы>` или у него
   своя схема (год, CRFN, «сосед справа»)?
4. Ему нужны только стороны, которые **делят межу**, или ещё «через улицу»/«сзади по
   кварталу»?
5. Что он делает, когда у соседа описания нет вовсе (частый случай в Staten Island:
   лот из filed map без deed с метесами) — берёт с налоговой карты?
6. Хранит ли он старые deeds (историю) или только актуальный?

## 9. Что проверить руками в первый же день (проба)

- По реальному BBL из «24 Alvine Avenue»: сколько документов в Legals, какие типы,
  сколько страниц у deed, есть ли текстовый слой в PDF ACRIS.
- Скачивается ли страница образом через `DocumentImageView`, или нужен браузер/сессия:
  если сайт отдаёт картинки только интерактивно, то «скачивание» делаем через браузер
  пользователя (открыть страницу), а распознавание и раскладку — сами.
- Как выглядит EXHIBIT A на деле 1990-х: качество скана и шрифт — от этого зависит,
  тянет ли Vision или нужен локальный OCR.
