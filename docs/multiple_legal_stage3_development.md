# Этап 3: экспериментальный поток в разработке

Этап 3 начат с разрешения пользователя, но **ещё не завершён и не включён по умолчанию**. Старый разбор и обычный путь отрисовки остаются прежними; в AutoCAD-писатель добавлен отдельный признак открытого обхода, который старые планы не используют. Переключатель `multiple_description_search.enabled` остаётся `false` по умолчанию. Никаких живых или платных запросов при разработке не выполнялось.

## Что подготовлено

- `multiple_description_pipeline.py` связывает поиск этапа 2 с подготовкой целых изображений выбранных страниц и многоконтурным разбором; вызовы моделей передаются извне. Этот координатор используется экспериментальным фоновым обработчиком приложения только под выключенным по умолчанию флагом.
- `multiple_description_parse.py` хранит отдельные описания, применяет лимит страниц, повторы, единичное уменьшение после явного отказа по размеру и выбор частичных ответов. Повреждённый список сторон допускает только непрерывную проверяемую начальную часть; пропущенную сторону не соединяет со следующей. Введена отдельная модель неполной части, чтобы одна–две стороны не притворялись замкнутым контуром.
- `multiple_description_transport.py` подготавливает одиночные OpenAI-совместимые вызовы; SDK-клиент создаётся без автоматических повторов. Ответы поиска и OCR в разбирающий запрос не передаются. Экспериментальный runtime умеет выбирать резерв `hydra / grok-4.7` с консервативным пределом 10 изображений при подтверждённом отсутствии Vision у выбранной модели; маршрут и предел **не проверены живым запросом** проверены только моками.
- `multiple_description_cache.py` сохраняет отдельный локальный `<имя.pdf>.multi-parse.json`: результаты, фактический контекст, историю и отдельно сведения портала. Кэш учитывает PDF, выбранные страницы и изображения, настройки рендера, модель, провайдера, инструкцию, схему и номер из имени. Старый контекст портала сохраняется; его изменение не вызывает переразбор. Нет копий изображений или исходного текста документа. Файл исключён из Git.
- `multiple_description_drawing.py` подготавливает планы нескольких описаний по источникам: дубли и роли не удаляются, номер берётся из имени, а непривязанные описания размещаются поодаль. В экспериментальном runtime привязка рассчитывается только при наличии улиц и явно указанной связи с перекрёстком, либо для явно указанного углового участка; разные PDF автоматически не объединяются. Это предварительная логика, ещё не проверенная на реальных данных. Для непривязанных описаний убираются вспомогательные линии и подписи, созданные старым построителем на основе выдуманного перекрёстка. Если старый построитель изменил сторону, изолированный путь сохраняет исходные векторы, а не подменяет их. Точное совпадение вспомогательных уличных элементов в одной группе не дублируется; частичные наложения пока не объединяются.
- Мост `multiple_description_runtime.py` соединяет обработку независимых PDF с формированием многоконтурной сцены, отдельным разрешением ключей RouterAI и выбранного провайдера, чтением номера портала и записью раздельных наблюдений в паспорт. Неподтверждённая поддержка Vision остаётся неизвестной, а не считается отказом; сбой сети не переключает модель. Ключи не включаются в `repr` цели или диагностические ошибки. Фоновый обработчик приложения использует этот мост только под выключенным по умолчанию флагом. Автоматическая связь разных PDF пока отсутствует.
- В приложении подготовлен отдельный список документов для будущего многоконтурного режима: можно независимо отметить несколько `our`, роли из паспорта учитываются без угадывания по номеру, а при передаче с Шага 0 выбираются полные PDF и не отбрасываются `our OLD`. Прежний список при выключенном флаге не меняется. Под флагом запуск использует отдельный фоновый обработчик и не обращается к старому одноконтурному парсеру. Добавление к прежней многоконтурной сцене повторно использует пригодный кэш; смешивание с прежней одноконтурной сценой не поддержано.
- `multiple_description_handoff.py` готовит неизменяемый пакет передачи результатов в GUI: пофайловые роли и состояния, все описания и дубли, планы или причину отсутствия плана. Отменённые, повреждённые или несогласованные пакеты отклоняются. Фоновый обработчик передаёт такой пакет в отдельную многоконтурную сцену GUI. Перед показом сверяются роли, порядок документов, SHA-256 и исходные векторы сторон. Неполная обработка и отсутствие выбранных поиском страниц не доказывают отсутствие описаний.
- Старое поле результата `PdfSetItem` дополнено списком результатов: непустой многоконтурный результат запрещено повторно использовать как одноконтурный кэш. Экспериментальная сцена приложения заполняет этот список. Отдельно добавлена явная принудительная команда переразбора через API: она сохраняет кэш поиска и передаёт актуальный номер портала.
- Подготовленная сцена GUI хранит все планы независимо от файлов, показывает контуры, номера и основные подписи в предпросмотре без выдуманного нуля и линии к нему. Старые автоматические развод соседей и их сверка для неё не запускаются. Черновик собирается из всех `our` без соседей и номеров; общий черновик и основные планы проверены только подставным AutoCAD. Очистка соседей сохраняет все наши контуры. Предпросмотр пока схематичен и не показывает все вспомогательные элементы, например угловые дуги. Команда отрисовки передаёт все доступные планы и черновик без нового запроса ИИ и повторно сверяет хеши PDF. Сбой одного файла не скрывает пригодные результаты остальных; сведения о положении и сбоях сохраняются в диагностике для разработчика.
- Кооперативная отмена между обработкой страниц и сетевыми попытками прекращает дальнейшие вызовы и не записывает отменённый разбор как завершённый. Уже отправленный запрос остановить нельзя; пользователь может понести его стоимость.
- Для одной или двух достоверных сторон создан открытый план с подписью в центре габаритов. `DrawPlan.open_traverse` не позволяет писателю AutoCAD его замкнуть даже в режиме полилиний; новые проверки используют только подставной AutoCAD. Для группы обычных полных `our` с подтверждённым общим перекрёстком подготовлен ограниченный общий черновик: один перекрёсток и 40 ft от ближайшей точки начала, без номеров `our`. Экспериментальная сборка черновика также сохраняет угловые, непривязанные и неполные планы без выдуманной привязки и без номеров, но полнота их оформления и положения перекрёстка ещё не подтверждена. Помощник рядовой группы возвращает причину вместо догадок при несовместимых привязках.
- Добавлены офлайн-тесты с синтетическими PDF и моками: сеть, ключи и реальные документы не используются.

## Что ещё необходимо перед завершением этапа

1. Найти и протестировать надёжный способ привязки **разных** PDF: сейчас даже совпадающие названия улиц не считаются достаточным доказательством связи, и группы разных файлов размещаются отдельно.
2. Завершить объединение общих улиц и оформление общего черновика для угловых, непривязанных и неполных описаний. Текущее поведение консервативное и не покрывает все случаи, в частности частично совпадающие уличные линии.
3. Доработать остальные элементы предпросмотра и жизненного цикла сцены, проверить обработку ошибок и AutoCAD за пределами подставного окружения. Разрешение ключей и резерв проверены моками; реальные ограничения Hydra и качество AI пока не подтверждены.
4. После завершения разработки представить результат; отдельно согласовать реальные платные проверки и включение режима. Переключатель не включать без согласия пользователя.

Существующий `AcadBuilder.plan()` требует минимум три стороны и способен применять правила построения замкнутого контура; его нельзя без изменений использовать для неполных частей. Аналогично прежний кэш одного участка нельзя считать полным многоконтурным результатом.
