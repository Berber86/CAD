# Patch notes 5.14 (2026-11-24)

## Свежие документы ACRIS: браузерный резерв вместо пропуска

Живой случай 3876: у соседа свежий MORTGAGE (CRFN 2026000329272, записан
20.11.2026), а NYC Open Data через месяц после записи CRFN не знает —
`document_id` не получить, документ пропускался.

Пользователь вручную подтвердил механику: клик **IMG** в результатах
поиска ACRIS открывает читалку сразу (`DocumentImageView?doc_id=
2026111700598001`), без промежуточных страниц и проверок. Заодно на двух
живых парах (2024000265906 → 2024101000085001 и 2026000329272 →
2026111700598001) видно: вычислить `document_id` из CRFN нельзя — префикс
это дата подготовки/записи, хвост — порядковый номер дня.

Что сделано:

- **Новый модуль `acris_browser.py`.** Если Open Data не дал `document_id`,
  программа открывает документ как человек: форма поиска ACRIS по BBL в
  новой вкладке браузера → район клавишами (Home + Down по коду) → Block,
  Lot → Search → строка с нужным CRFN (сверка только по цифрам) → клик IMG.
  Проверка — результатом: открылась именно читалка. Промах в DET (кнопка
  левее) лечится шагом назад и кликом правее. Любой сбой — снимок
  «чёрного ящика» в папку задания и честная ошибка.
- **`acris_viewer.download_pdf_via_viewer(already_open=True)`**: читалка
  уже открыта кликом — URL не трогаем, ждём живую страницу и дальше как
  обычно (дискета → OK → PDF из «Загрузок»).
- **`deed_intake`**: адаптированная строка без `document_id` несёт CRFN;
  загрузчик по нему идёт в браузерный резерв (`crfn_opener`), а не
  пропускает документ. В журнал пишется, что документ открывается кликом
  IMG. Старое поведение (пропуск с причиной) осталось только там, где
  загрузчик задан извне (тесты/ручные пути).

Основной путь не изменён: если Open Data знает CRFN — всё как раньше.
