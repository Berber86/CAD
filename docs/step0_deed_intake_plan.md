# Шаг 0. Сбор описаний (legal descriptions) — наш участок и соседи

Шаг 0 идёт **перед** Шагом 1 и создаёт для него вход: набор описаний, по которому Шаг 1
строит участок и делает акт сверки. Значит опираться на Шаг 1 нельзя — его ещё нет.
Ниже — что у нас есть на входе, что Шаг 0 обязан выдать и как проверять найденное,
пока ни одного полигона не построено.

## 1. Вход и выход

**Вход (то, что есть на старте заказа):**

- **адрес дома** — «24 Alvine Avenue, Staten Island» (может быть с опечаткой, может быть
  только BBL из бумаг);
- **DWG от геодезиста** — чертёж участка **без мировых координат** (локальные координаты,
  ось «вдоль улицы»); в нём есть адрес, номер квартала/лота в тексте, размеры сторон,
  контур дома, соседи, иногда подпись «as shown on tax map»;
- фото и скетч с поля — они нужны **расширенному Шагу 2**, в Шаге 0 не участвуют.

**Выход Шага 0 — папка описаний для Шага 1:**

```
<папка проекта>/
  01_описания/
    OUR 32 NEW.pdf             # наш участок, самый свежий документ (схема Коли)
    OUR 32 OLD.pdf             # наш участок, самый старый документ
    LOT 30 NEW.pdf             # сосед — только свежий
    OUR 32 NEW_p4-6.pdf        # обрезанная копия: только страницы описания
    OUR 32 NEW.json            # паспорт: откуда взят, что за документ, страницы
    _manifest.json             # состав набора: роли, страницы, BBL, итоги проверок
```

`_manifest.json` — главный результат: по нему Шаг 1 поднимает набор **одной кнопкой**
(уже с ролями и страницами), а не выбором файлов в диалоге.

## 2. Чего у нас нет — и почему это не мешает

| Чего нет | Почему не мешает |
|---|---|
| Мировых координат у чертежа | Шагу 0 они не нужны: всё делается «на бумаге» — адрес, BBL, документы, самопроверка описаний. Геореференсинг (одна контрольная точка + истинные румбы) — отдельная задача, и не первая |
| Полигона нашего участка | Он появится как раз из описания, которое найдёт Шаг 0. Проверки ниже построены так, чтобы работать **до** появления полигона |
| Результатов Шага 1 (акт сверки) | Общие межи проверяются попарно между самими описаниями (§5), без «нашего» построения |
| Интернета (бывает) | Шаг 0 работает и как **ручная раскладка**: перетащил скачанные PDF — программа обрежет страницы, назовёт файлы, проверит и соберёт `_manifest.json` |

## 3. Что Шаг 0 берёт из DWG геодезиста

DWG — не источник координат, но источник **подсказок и третьего мнения**:

1. **Адрес и block/lot текстом** — если в чертеже написано `BLOCK 1234 LOT 32`, это
   подтверждение BBL, полученного из адреса (а если адрес не находится — единственная
   зацепка).
2. **Размеры сторон** — геодезист мерил сам. Совпадение с deed — хорошо; расхождение
   (deed 174.89 / на чертеже 176.9) — это уже знакомая нам «две длины одной стороны»,
   и Шаг 0 просто фиксирует третье число, ничего не решая.
3. **Какая сторона — улица** (по подписям, по контуру дома, по въезду) — пригодится для
   ролей соседей и для формулировок отчёта.
4. **Контуры соседних домов** — сколько соседей вообще примыкает.

Чего DWG не даёт: названий лотов соседей и их описаний. Это и есть работа Шага 0.

## 4. Адрес → BBL

1. `geosearch.planninglabs.nyc` (бесплатно, без ключа): адрес → lat/lon + **BBL** + BIN.
2. Подтверждение: block/lot из DWG (если есть), номер дома из адреса против описания.
3. Если адрес неоднозначен (угловой участок, «rear lot»): предложить варианты списком с
   BBL и площадью — пусть выберет человек, а не программа.
4. BBL — единственный «якорь» всего Шага 0: по нему берутся документы ACRIS и геометрия
   лотов города.

## 5. Документы: Richmond County Clerk (и ACRIS для других районов)

Схема Коли (15.11.2026, по его видео) — **Staten Island берётся не в ACRIS**:

1. По block/lot открывается список документов участка:

   ```
   https://www.richmondcountyclerk.com/Search/ShowResultsBlocks/0?Block=6323&Lot=32&SelectedDocumentIdentifier=0
   ```

2. В списке берутся строки **Deed**; если Deed нет — **Mortgage**.
3. Строка открывает карточку `/Search/ViewDocumentInfo/<номер>`, а из неё —
   сам PDF: `/ViewVscmsDocument/ViewContent?p_endorsementId=<номер>`.
4. Для **нашего** лота качаются **самый свежий и самый старый** документ;
   для **соседей** — только свежий (старый оставлен функцией на случай проблем
   с межой соседа — `with_old_for_neighbour`).
5. Имя файла: `OUR 32 NEW.pdf` / `OUR 32 OLD.pdf`; сосед — `LOT 30 NEW.pdf`.
6. Хранится **и целый документ, и обрезанная копия** (заказчик, 15.11.2026): целый —
   `OUR 32 NEW.pdf`, только описание — `OUR 32 NEW_p4-6.pdf`. Страницы ищет
   `deed_pages.find_description_pages` (текстовый слой, а для скана — локальный OCR),
   режет `deed_pages.trim_pdf`. Шаг 1 читает обрезанную копию: страницы уже в имени.

**Cloudflare и лестница скачивания** (решение заказчика 15.11.2026: «начиная с
самого автоматизированного, а при неудаче — на шаг ниже»):

1. **Прямое скачивание** (`rcclerk.download_pdf`). Если Cloudflare не мешает — файл
   наш, браузер не нужен.
2. **Браузер сам**: программа открывает ссылку в браузере по умолчанию и ждёт, пока в
   «Загрузках» появится новый PDF (проверка на бота проходит сама, минуты за три).
   Файл подхватывается из загрузок и копируется в папку описаний — от человека нужно
   только подождать. Недокачанные файлы (`.crdownload`) и файлы без сигнатуры `%PDF-`
   не принимаются: лучше подождать, чем сохранить обрезанный документ.
3. **Ручной шаг**: если браузер не открылся или файл не появился за отведённое время —
   `ManualStepNeeded` с готовой ссылкой и папкой: открыть, дождаться, положить PDF.

Всё это — `rcclerk.download_with_fallback(...)`, который возвращает ещё и ступень
(`direct` / `browser`), чтобы в отчёте было видно, чем обошлось.

**Другие районы.** Для Manhattan / Bronx / Brooklyn / Queens документы лежат в
ACRIS, и там работает прежняя схема с открытыми данными:

| Набор | ID | Что даёт |
|---|---|---|
| ACRIS Real Property Legals | `8h5j-fqxa` | `document_id` по borough + block + lot |
| ACRIS Real Property Master | `bnx9-e6tj` | тип (`DEED`, `MTGE`…), CRFN, даты |
| ACRIS Real Property Parties | `636b-3b5g` | продавец/покупатель |
| ACRIS Real Property References | `pwkr-dpni` | цепочка «being the same premises…» |

Это следующий шаг: сейчас сделан Richmond (там работает заказчик), ACRIS —
по той же логике выбора документов (`choose_documents`) и того же хранения.

## 6. Соседи — из городской геометрии, а не из нашего чертежа

1. BBL → полигон лота города (MapPLUTO на NYC Open Data).
2. Соседи — лоты, у которых с нашим есть общий отрезок границы (допуск ~1 ft).
3. Роли «справа / слева / сзади / через улицу» — по азимуту от центра участка на центр
   соседа (стороны света честные, потому что румбы в описании истинные).
4. Соседей сортируем по длине общей межи: сначала те, с кем делим самую длинную
   границу, — именно они и нужны Шагу 1 для сверки.

## 7. Проверка найденного без Шага 1 — пять независимых проверок

Все пять работают **до** построения полигона и без мировых координат:

1. **Замыкание описания.** Парсим метесы и границы, строим полигон, считаем невязку.
   Настоящий deed замыкается в доли фута; 3 ft — ошибка распознавания или не тот документ.
2. **Площадь против города.** Площадь полигона против `lot_area` из PLUTO (±5 %);
   больше — объяснять.
3. **Общая межа с соседом.** У нашего deed есть линия 176.92 ft румбом `S 22°26'12" E`;
   у соседа должна найтись линия той же длины с **обратным** румбом (`N 22°26'12" W`).
   Это сравнение векторов, никакой сборки не нужно — и это самый сильный сигнал, что
   оба документа про эти самые две межи.
4. **Улица и номер дома.** Название улицы из описания против адреса; номер дома —
   против адреса и против текста в DWG.
5. **Третье мнение — чертёж геодезиста.** Длины сторон на DWG против deed; расхождение
   не «лечим», а показываем числом.

Итог по каждому файлу — в отчёт и в `_manifest.json`:

```
LOT 30 (BBL 5-1234-30, сосед слева)
  deed 1998-06-14, CRFN 1998000123456, стр. 2–3, 4 стороны
  невязка 0.02 ft · площадь 3 998 против 4 000 по городу
  общая межа 176.92 ft S 22°26'12" E — совпадает с нашей стороной #2
  на чертеже геодезиста 176.9 → принят
```

и честное «не принят»:

```
LOT 34 (BBL 5-1234-34, сосед сзади)
  новый deed 2019 г. — без метесов, ссылка на CRFN 2004123456789
  в нём невязка 11.4 ft, площадь 5 210 против 3 640 → не принят, нужен глаз геодезиста
```

## 8. Как из скана получается текст (сделано в Шаге 1, версия 3.9)

В ACRIS **нет текстового слоя** — это сканы, `PyMuPDF` отдаёт по ним 0 символов.
Значит нужен OCR, и его можно сделать **бесплатно и локально**, без ИИ.

**Проба** (`docs/ocr_probe.py`, песочница 2026-11-15, CPU без GPU, 400 dpi): страница
«EXHIBIT A» с румбами `N 22°26'12" E, 100.05 feet` — **около 5 с на страницу**, все румбы и
длины распознаны. Выше 400 dpi вреда больше, чем пользы (600 dpi на самом мелком шрифте
распознал хуже), поэтому разрешение не растят, а при неудаче страницу режут на куски 2×2. Косметика: у «BEGINNING AT A POINT» поехал регистр (`PoINT`), после
запятых пропадают пробелы (`THENCES 67°33'48"E`) — нашему парсеру это не мешает, он
нормализует текст.

Стек: `rapidocr-onnxruntime` (чистый `pip`, ONNX, без внешнего бинарника и без
Ghostscript; на Windows работает так же). Вес: 16 МБ сам пакет + 78 МБ `onnxruntime` +
72 МБ `opencv-python-headless` ≈ **166 МБ**. Поэтому — **необязательная зависимость**:
есть пакет — работает локальный OCR, нет — сразу идём в Vision (как сейчас).

Схема разбора страниц:

1. **миниатюры + локальный OCR** страницы (0 ₽, 400 dpi, но не выше dpi картинки в PDF):
   ищем `BEGINNING AT A POINT`,
   `THENCE`, румбы — так отбираются 2–4 страницы описания из 12;
2. **полный локальный OCR** этих страниц → `LOT 30.txt`;
3. **проверка замыканием** (§7): сошлось в доли фута — готово, ИИ не нужен ни разу;
4. **не сошлось** — значит OCR перепутал цифру; вот **эту страницу** (а не весь пакет)
   отправляем в Vision с вопросом «проверь числа». Платно, но редко и по одной странице;
5. результат — `LOT 30.txt` в нормализованном виде, чтобы повторные запуски не требовали
   ни PDF, ни OCR, ни ИИ.

Геометрия здесь работает детектором ошибок распознавания: неверная цифра почти всегда
ломает замыкание, поэтому «дорогой» разбор включается сам и только там, где он нужен.

**Это уже работает в Шаге 1** (`ocr_pages.py` + `pdf_set.resolve_ocr_source`, версия 3.9):
скан в наборе распознаётся в фоне, кэшируется и разбирается бесплатно, а при невязке
больше 0.08 ft выдаёт замечание «переключите файл на ИИ». Шагу 0 остаётся то же самое
плюс отбор страниц (`deed_pages`) и запись результата рядом с PDF (`LOT 30.txt`).

Скан 1970-х с микрофильма может не распознаться вовсе: тогда так и пишем, а не выдумываем
описание.

## 9. Если описания нет совсем

Частый случай в Staten Island: лот из filed map, deed с метесами отсутствует. Тогда:

- пробуем **налоговую карту** блока (DOF Digital Tax Map): на ней проставлены размеры —
  этого хватает, чтобы Шаг 1 мог построить контур, а мы пометили источник;
- пробуем **filed map** по ссылке из deed («as shown on a map entitled … filed in the
  Richmond County Clerk's office») — это отдельная, тяжёлая история; в первой версии
  только помечаем, что нужна карта, и даём номер;
- пишем `LOT 34 — описания нет.txt`: что искали (block/lot, даты, типы документов),
  что нашли, чего не хватает и что нужно от геодезиста.

Молча пропустить лот нельзя: Шаг 1 должен получить **полный** список, включая «здесь
дыра».

## 10. `_manifest.json` — контракт между Шагом 0 и Шагом 1

```json
{
  "version": 1,
  "address": "24 Alvine Avenue, Staten Island",
  "bbl": "5-1234-32",
  "created": "2026-11-16T10:12:00",
  "items": [
    {
      "file": "OUR 32 NEW_p4-6.pdf",
      "text": "OUR 32 NEW.txt",
      "lot": "32",
      "role": "main",
      "side": null,
      "bbl": "5-1234-32",
      "endorsement_id": "2640218",
      "crfn": "2019000123456",
      "doc_type": "DEED",
      "doc_date": "2019-05-14",
      "recorded": "2019-06-14",
      "parties": ["SMITH JOHN", "JONES MARY"],
      "pages": "4-6",
      "source_url": "https://www.richmondcountyclerk.com/ViewVscmsDocument/ViewContent?p_endorsementId=2640218",
      "downloaded": "2026-11-16T10:10:41",
      "checks": {"closure_ft": 0.006, "area_sqft": 4000, "city_area_sqft": 4000,
                 "shared_line": null, "street": "ALVINE AVENUE"},
      "accepted": true,
      "notes": []
    }
  ],
  "missing": [{"lot": "34", "bbl": "5-1234-34", "reason": "deed без метесов, map не найден"}]
}
```

Шаг 1 читает `items`, ставит первую запись как «наш участок», остальные — как соседей,
и берёт страницы из `pages` (то же, что уже понимает `_p4-6` в имени файла).

## 11. Модули и порядок работ

| Модуль | Что делает | Зависимости |
|---|---|---|
| `rcclerk.py` | адреса списка/карточки/PDF, разбор строк (Deed/Mortgage, даты), правило «свежий + старый», имена файлов, скачивание с честной ошибкой Cloudflare | — |
| `deed_store.py` | папка `01_описания`: имена `OUR 32 NEW.pdf` (+`_p4-6`), паспорт `.json` рядом, `_manifest.json`, поиск дублей по номеру клерка | — |
| `deed_pages.py` | поиск страниц с описанием (текстовый слой → локальный OCR) и обрезка копии `_p4-6` | `ocr_pages`, PyMuPDF |
| `deed_pages.py` | поиск страниц с описанием (миниатюры → Vision), обрезка, склейка | PyMuPDF, `llm_parser` |
| `deed_verify.py` | пять проверок §7 → «принят / проверить», третий голос с DWG | существующий парсер |
| `acris.py` | BBL → документы (Legals + Master + References), отбор DEED, скачивание страниц с кэшем и троттлингом | `urllib`, `pyproj` не нужен |
| `lots_near.py` | адрес → BBL; соседи по городской геометрии; роли по азимуту | geosearch, MapPLUTO |
| `main.py` | новая **вкладка «Шаг 0»** первой: адрес, DWG, кнопки «Собрать описания» / «Открыть папку описаний», отчёт | — |

Порядок, при котором польза появляется сразу:

1. `deed_store` + вкладка с ручной раскладкой → уже экономит время и поднимает набор
   одной кнопкой (работает без интернета и без ACRIS);
2. `deed_pages` (обрезка страниц, имя файла) → перестаём скачивать лишнее;
3. `deed_verify` → перестаём бояться, что взяли не тот документ;
4. `acris` + `lots_near` → собственно автоматический сбор нашего и соседских лотов.

## 12. Право и аккуратность

- ACRIS — публичный реестр; скачивание для своей работы нормально. Не строить из этого
  базу для перепродажи, не публиковать образы, в паспорте указывать источник.
- Вежливость: ≤1 запроса в секунду, пауза между документами, кэш, при 429/503 — пауза
  и повтор. Никакого параллельного долбления.
- Скан плохого качества — честное «не распознано», а не выдуманное описание.

## 13. Что спросить у Коли, когда покажет свой алгоритм

1. ACRIS или платный сервис (title company, PropertyShark, TLO)? От этого зависит,
   возможна ли автоматизация вообще.
2. В его DWG есть номер блока и лота текстом? Это подтверждение BBL или единственная
   зацепка — надо знать заранее.
3. Имя файла: `LOT 30.pdf` + страницы в имени (`_p2-3`) или своя схема (год, CRFN)?
4. Берёт самый свежий deed или тот, где есть метесы? Старые deeds хранит?
5. Что делает, когда у соседа описания нет совсем — берёт с налоговой карты? Какую
   пометку ставит, чтобы не забыть?
6. Нужны соседи только по меже или ещё «через улицу»/«сзади по кварталу»?
7. Скачивает он страницы по одной или документ целиком, и режет ли обложки?

## 14. Проба на реальном заказе (следующий шаг)

- Открыть в браузере `ShowResultsBlocks/0?Block=6323&Lot=32`, сохранить страницу
  и прогнать её через `rcclerk.parse_document_rows` — увидеть, все ли строки
  нашлись с типами и датами (разбор терпимый, но настоящий HTML мы ещё не видели).
- Скачать `OUR 32 NEW.pdf` и `OUR 32 OLD.pdf` (руками, через браузер) и прогнать
  через локальный OCR: есть ли описание, на каких страницах, замыкается ли контур.
- Проверить, что `_manifest.json` поднимает набор в Шаге 1 одним нажатием.
- По соседям: взять 2–3 лота по меже, убедиться, что «свежий» документ есть и что
  общая межа с нашим описанием совпадает (обратный румб той же длины).
